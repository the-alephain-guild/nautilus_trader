# 编码规范

## 代码风格

当前代码库可作为格式化约定的参考。
以下提供了更多指导。

### 通用格式化规则

以下规则适用于**所有**源文件（Rust、Python、Cython、shell 等）：

- 只使用**空格**，不使用制表符。
- 行宽一般应保持在 **100 个字符**以下；必要时合理换行。
- 使用美式英语拼写（`color`、`serialize`、`behavior`）。

### Shell 脚本可移植性

本仓库中的 shell 脚本使用 **bash**（非 POSIX sh），且必须在 **Linux** 和 **macOS** 上可移植。面向用户的脚本（如 `scripts/cli/install.sh`）还必须能在 **Windows** 上通过 Git Bash 或 WSL 运行。

**Shebang**：始终使用 `#!/usr/bin/env bash` 以确保可移植性。

**常见陷阱**：GNU 和 BSD 工具在 Linux 和 macOS 之间存在差异：

| 命令               | Linux (GNU)      | macOS (BSD)       | 可移植方案                      |
| ---------------- | ---------------- | ----------------- | -------------------------- |
| `sed -i`         | `sed -i 's/…'`   | `sed -i '' 's/…'` | 使用备份扩展名：`sed -i.bak 's/…'` |
| `stat`（文件大小）     | `stat -c%s file` | `stat -f%z file`  | 通过 `stat --version` 检测     |
| `sha256sum`      | `sha256sum file` | 不可用               | 使用 `shasum -a 256` 或检测     |
| `readlink -f`    | 可用               | 不可用               | 避免使用，或用 `realpath`         |
| `grep -P` (PCRE) | 可用               | 不可用               | 改用 `-E`（扩展正则表达式）           |
| `date`（纳秒）       | `date +%N`       | 不可用               | 使用 `$RANDOM` 防止缓存          |

**Bash 版本**：macOS 自带 bash 3.2；面向用户的脚本中应避免使用 bash 4+ 特性：

| 特性                           | Bash 版本 | 替代方案                            |
| ---------------------------- | ------- | ------------------------------- |
| 关联数组（`declare -A`）           | 4.0+    | 使用文件或简单数组                       |
| `readarray` / `mapfile`      | 4.0+    | 使用 `while read` 循环              |
| `${var,,}` / `${var^^}`（大小写） | 4.0+    | 使用 `tr '[:upper:]' '[:lower:]'` |

**CI 脚本**（`scripts/ci/*`）运行在 Linux runner 上，因此可以使用 bash 4+ 和 GNU 工具。

### 注释约定

1. 通常在每个注释块或文档字符串上方留**一个空行**，使其与代码在视觉上分隔。
2. 使用*句首大写* -- 首字母大写，其余小写（专有名词或缩写词除外）。
3. 句号后不要使用双空格。
4. **单行注释***不得*以句号结尾，*除非*该行以 URL 或内联 Markdown 链接结尾 -- 这种情况下保留链接所需的标点。
5. **多行注释**应使用逗号分隔句子（而非每行一个句号结尾）。最后一行*应该*以句号结尾。
6. 注释要简洁；注重清晰度，只解释不明显的内容 -- *少即是多*。
7. 避免在文本中使用表情符号。

### 文档注释语气

**Rust** 文档注释应使用**陈述语气（indicative mood）** -- 例如 *"Returns a cached client."*

该约定与 Rust 生态的主流风格一致，使生成的文档对最终用户更加自然。

### 术语和用词

1. **错误消息**：避免在错误消息中使用 ", got"。根据上下文使用更具描述性的替代方式，如 ", was"、", received" 或 ", found"。
   - 不推荐：`"Expected string, got {type(value)}"`
   - 推荐：`"Expected string, was {type(value)}"`

2. **拼写**：使用 "hardcoded"（一个词）而非 "hard-coded" 或 "hard coded" -- 这是更现代和通用的拼写方式。

3. **错误变量命名**：捕获的错误/异常使用单字母 `e`：
   - Rust：使用 `Err(e)` 而非 `Err(err)` 或 `Err(error)`，闭包中使用 `|e|` 而非 `|err|`
   - Python：使用 `except SomeError as e:` 而非 `as err:` 或 `as error:`

### 命名约定

1. **内部字段**：私有/内部字段可以使用缩写（如 `_price_prec`、`_size_prec`）以保持热路径代码简洁。

2. **面向用户的 API**：公共属性、函数参数、返回类型以及指标名称/标签应使用完整的描述性名称（如 `price_precision`、`size_precision`）。这可以防止缩写术语泄漏到仪表盘或告警中。

3. **错误消息和日志**：使用完整词汇以保证清晰度（如 "price precision" 而非 "price prec"）。用户不应看到缩写术语。

### 格式化

1. 对于较长的代码行以及传递多个参数时，应换行并在下一个逻辑缩进处对齐（而不是尝试在左括号处做"美观"对齐）。这种做法节省了右侧空间，确保重要代码更居中显示，并且对函数/方法名称的更改也更具鲁棒性。

2. 右括号应位于新行，与逻辑缩进对齐。

3. 同时确保多个悬挂参数或实参以尾随逗号结尾：

```python
long_method_with_many_params(
    some_arg1,
    some_arg2,
    some_arg3,  # <-- 尾随逗号
)
```

## 提交消息

以下是提交消息的风格指南：

1. 标题行限制在 60 个字符以内。标题首字母大写，不以句号结尾。

2. 使用"祈使语气"，即消息应描述应用该提交后会做什么。

3. 可选：使用正文解释更改。与标题之间用空行分隔。宽度保持在 100 字符以内。可以使用带或不带句号结尾的要点列表。

4. 可选：提供相关 issue 或工单的 # 引用。

5. 可选：提供有参考价值的超链接。

### Gitlint（可选）

Gitlint 可以帮助自动强制执行提交消息规范。它会检查提交消息是否遵循上述指南（字符限制、格式等）。这是**可选启用**的，不在 CI 中强制执行。

**好处**：鼓励简洁而富有表达力的提交消息，有助于培养对更改进行清晰说明的习惯。

**安装**：首先在本地安装 gitlint：

```bash
uv pip install gitlint
```

将 gitlint 启用为自动 commit-msg 钩子：

```bash
prek install --hook-type commit-msg
```

**手动使用**：检查最近一次提交消息：

```bash
gitlint
```

配置位于仓库根目录的 `.gitlint` 文件中：

- **60 字符标题限制**：确保在 GitHub 上清晰显示，鼓励在描述性的同时保持简洁。
- **79 字符正文宽度**：与 Python 的 PEP 8 约定及 git 工具的传统限制一致。

:::note
Gitlint 未来可能会在 CI 中强制执行，因此尽早采用这些实践有助于确保平滑过渡。
:::
