# 模拟订单 (Emulated orders)

## 简介

订单模拟让你即便在交易场所不原生支持某些订单类型时，依然可以使用这些订单类型。

Nautilus 会在本地模拟这些订单类型（例如 `STOP_LIMIT` 或 `TRAILING_STOP` 订单）的行为，
而在场所上实际执行时只使用 `MARKET` 和 `LIMIT` 订单。

当你创建一个模拟订单时，Nautilus 会持续追踪某一特定类型的市场价格（由 `emulation_trigger`
参数指定），并根据你设定的订单类型和条件，在触发条件满足时自动提交相应的基础订单
（`MARKET` / `LIMIT`）。

例如，如果你创建了一个模拟的 `STOP_LIMIT` 订单，Nautilus 会持续监控市场价格，直到达到你的 `stop`
价格，然后自动向场所提交一个 `LIMIT` 订单。

为了执行模拟，Nautilus 需要知道它应该监控**哪种类型的市场价格**。
默认情况下，它使用买价和卖价（报价），这也是为什么你会经常在示例中看到 `emulation_trigger=TriggerType.DEFAULT`
（这等价于使用 `TriggerType.BID_ASK`）。不过，Nautilus 还支持各种其他价格类型，
用以指导模拟过程。

## 提交订单进行模拟

模拟一个订单的唯一要求，就是向 `Order` 构造函数或 `OrderFactory` 创建方法的 `emulation_trigger`
参数传入一个 `TriggerType`。目前支持以下模拟触发类型：

- `NO_TRIGGER`：完全禁用本地模拟，订单将整体提交到场所。
- `DEFAULT`：与 `BID_ASK` 相同。
- `BID_ASK`：使用报价进行触发的模拟。
- `LAST_PRICE`：使用成交进行触发的模拟。

触发类型的选择决定了订单模拟的行为方式：

- 对于 `STOP` 订单，触发价格会与指定的触发类型进行比较。
- 对于 `TRAILING_STOP` 订单，跟踪偏移量会基于指定的触发类型进行更新。
- 对于被模拟的 `LIMIT` 订单，限价会与指定的触发类型进行比较，以确定何时将该订单作为 `MARKET` 订单释放。

以下是你可以设置到 `emulation_trigger` 参数中的所有可用取值及其用途：

| 触发类型              | 描述                             | 常见使用场景                           |
| :---------------- | :----------------------------- | :------------------------------- |
| `NO_TRIGGER`      | 完全禁用模拟。订单将直接发送到场所，不进行任何本地处理。   | 当你想使用场所的原生订单处理，或对于不需要模拟的简单订单类型时。 |
| `DEFAULT`         | 与 `BID_ASK` 相同。这是大多数模拟订单的标准选择。 | 当你想使用"默认"类型的市场价格进行通用模拟时。         |
| `BID_ASK`         | 使用最优买价和卖价（报价）来指导模拟。            | 应对当前市场价差做出反应的止损单、跟踪止损单及其他订单。     |
| `LAST_PRICE`      | 使用最近一笔成交的价格来指导模拟。              | 应基于实际已成交交易而非报价触发的订单。             |
| `DOUBLE_LAST`     | 使用两笔连续的最新成交价来确认触发条件。           | 当你想在触发前对价格变动进行额外确认时。             |
| `DOUBLE_BID_ASK`  | 使用两次连续的买价/卖价更新来确认触发条件。         | 当你想在触发前对报价变动进行额外确认时。             |
| `LAST_OR_BID_ASK` | 在最新成交价或买价/卖价上触发。               | 当你想对任何类型的价格变动都更具响应性时。            |
| `MID_POINT`       | 使用最优买价和卖价之间的中间点。               | 应基于理论公允价格触发的订单。                  |
| `MARK_PRICE`      | 使用标记价格（在衍生品市场中常见）进行触发。         | 对期货和永续合约尤其有用。                    |
| `INDEX_PRICE`     | 使用底层指数价格进行触发。                  | 当交易跟踪某个指数的衍生品时。                  |

## 技术细节

无论某种订单类型是否在交易场所上受支持，平台都能在本地模拟绝大多数订单类型。
订单模拟的逻辑和代码路径在所有[环境上下文 (environment contexts)](../architecture.md#environment-contexts)中
完全相同，并使用一个共用的 `OrderEmulator` 组件。

:::note
对每个运行实例所能拥有的模拟订单数量没有限制。
:::

## 生命周期

一个模拟订单会经历以下阶段：

1. 由 `Strategy` 通过 `submit_order` 方法提交。
2. 发送到 `RiskEngine` 进行交易前风险检查（在此阶段可能被拒绝）。
3. 发送到 `OrderEmulator`，在其中被*持有* / 模拟。
4. 一旦触发，模拟订单会被转换为 `MARKET` 或 `LIMIT` 订单并被释放（提交到场所）。
5. 被释放的订单在提交到场所之前会经历最终的风险检查。

:::note
模拟订单与*常规*订单受相同的风险控制约束，并且可以由交易策略以正常方式进行修改和取消。
在取消所有订单时，它们同样会被包含在内。
:::

:::info
模拟订单在其整个生命周期中都会保留其原始的客户端订单 ID，从而便于通过缓存进行查询。
:::

### 被持有的模拟订单

对于一个现在由 `OrderEmulator` 组件*持有*的模拟订单，将发生以下情况：

- 原始的 `SubmitOrder` 命令将被缓存。
- 模拟订单将在本地的 `MatchingCore` 组件内部进行处理。
- `OrderEmulator` 将订阅任何所需的市场数据（如果尚未订阅）以更新撮合核心。
- 模拟订单在被*释放*或取消之前，可以被修改（由交易者）和更新（由市场）。

### 被释放的模拟订单

一旦数据的到来在本地触发 / 匹配了某个模拟订单，将发生以下*释放*动作：

- 订单将通过一个额外的 `OrderInitialized` 事件被转换为 `MARKET` 或 `LIMIT` 订单（见下表）。
- 订单的 `emulation_trigger` 将被设置为 `NONE`（它将不再被任何组件视为模拟订单）。
- 附加在原始 `SubmitOrder` 命令上的订单将被送回 `RiskEngine` 进行额外检查，因为它可能经历过任何修改/更新。
- 如果未被拒绝，命令将继续传递到 `ExecutionEngine`，并照常通过 `ExecutionClient` 发送到交易场所。

## 可以被模拟的订单类型

下表列出了哪些订单类型可以被模拟，以及它们在被释放并提交到交易场所时会转换为哪种订单类型。

| 用于模拟的订单类型              | 可模拟  | 释放后的类型   |
| :--------------------- | :--- | :------- |
| `MARKET`               |      | 不适用      |
| `MARKET_TO_LIMIT`      |      | 不适用      |
| `LIMIT`                | ✓    | `MARKET` |
| `STOP_MARKET`          | ✓    | `MARKET` |
| `STOP_LIMIT`           | ✓    | `LIMIT`  |
| `MARKET_IF_TOUCHED`    | ✓    | `MARKET` |
| `LIMIT_IF_TOUCHED`     | ✓    | `LIMIT`  |
| `TRAILING_STOP_MARKET` | ✓    | `MARKET` |
| `TRAILING_STOP_LIMIT`  | ✓    | `LIMIT`  |

## 查询

在编写交易策略时，可能需要了解系统中模拟订单的状态。
有多种方式可以查询模拟状态：

### 通过缓存

可使用以下 `Cache` 方法：

- `self.cache.orders_emulated(...)`：返回当前所有的模拟订单。
- `self.cache.is_order_emulated(...)`：检查某个特定订单是否被模拟。
- `self.cache.orders_emulated_count(...)`：返回模拟订单的数量。

更多细节请参阅完整的 [API 参考](/docs/python-api-latest/cache.html)。

### 直接查询订单

你可以直接使用以下方式查询订单对象：

- `order.is_emulated`

如果其中任一返回 `False`，则该订单已从 `OrderEmulator` 中*释放*，
因此不再被视为模拟订单（或者它从来就不是模拟订单）。

:::warning
不要持有对模拟订单的本地引用。当模拟订单被*释放*时，订单对象会发生转换。
请改用 `Cache`。
:::

## 持久化与恢复

如果一个正在运行的系统在存在活跃模拟订单的情况下崩溃或关闭，那么这些订单将从任何已配置的缓存数据库中
被重新加载到 `OrderEmulator` 内部。
这能在系统重启和恢复过程中保留订单状态。

## 最佳实践

在使用模拟订单时，请考虑以下最佳实践：

1. 始终使用 `Cache` 来查询或追踪模拟订单，而不要存储本地引用
2. 注意模拟订单在被释放时会转换为不同的类型
3. 记住模拟订单在提交和释放两个环节都会经历风险检查

:::note
订单模拟允许你即便在不原生支持高级订单类型的场所上也能使用这些类型，
从而让你的交易策略在不同场所之间更具可移植性。
:::
