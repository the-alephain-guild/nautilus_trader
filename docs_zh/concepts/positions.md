# 持仓 (Positions)

本指南介绍 NautilusTrader 中持仓 (position) 的工作原理，包括其生命周期、从订单成交 (order fill) 中的聚合方式、盈亏计算，以及净额 (netting) 订单管理系统 (OMS) 配置中持仓快照的重要概念。

## 概述

持仓代表对市场中某一特定金融工具 (instrument) 的持有敞口。持仓是跟踪交易表现和风险的基础，它汇总了特定金融工具的所有成交，并持续计算未实现盈亏 (unrealized PnL)、平均入场价格和总敞口等指标。

系统在订单成交时自动创建持仓，并从开仓到平仓全程跟踪。平台通过 OMS（订单管理系统）配置支持净额和对冲 (hedging) 两种持仓管理方式。

:::note 什么是敞口（Exposure）？
**敞口** = 持仓量 × 市场价格，代表你有多少资金正在承受市场波动的风险。敞口越大，同样的价格变动对盈亏影响越大。

- 持有 1 BTC（$60,000）→ 敞口 $60,000，市场波动 1% 盈亏 $600
- 空仓（FLAT）→ 敞口为 0，不承担任何市场风险
- 做空 2 BTC → 敞口 $120,000，方向相反但风险暴露金额相同

本文档中"增加/减少敞口"指风险暴露的变化；"净敞口"（`signed_qty`）指买卖对冲后的净头寸；"峰值数量"（`peak_qty`）指持仓期间承受过的最大风险。
:::

## 持仓生命周期

### 创建

系统在首次成交时开仓：

- **净额 OMS**：在某一金融工具首次成交时开仓（每个金融工具仅一个持仓）。
- **对冲 OMS**：在新 `position_id` 首次成交时开仓（每个金融工具可有多个持仓）。

持仓跟踪以下信息：

- 开仓订单和成交详情。
- 入场 (entry) 方向（`LONG` 或 `SHORT`）。
- 初始数量 (quantity) 和平均价格。
- 初始化和开仓的时间戳。

:::tip
你可以在 actor/策略 (strategy) 中通过缓存访问持仓，使用 `self.cache.position(position_id)` 或 `self.cache.positions(instrument_id=instrument_id)`。
:::

### 更新

随着后续成交的发生，持仓会：

- 汇总买入和卖出成交的数量。
- 重新计算平均入场和出场 (exit) 价格。
- 更新峰值数量（达到的最大敞口）。
- 跟踪所有关联的订单 ID 和交易 ID。
- 按币种累计佣金。

### 平仓

当净数量变为零（`FLAT`，即空仓）时，持仓关闭。平仓时：

- 记录平仓订单 ID。
- 计算从开仓到平仓的持续时间。
- 计算最终已实现盈亏 (realized PnL)。
- 在净额 OMS 中，当持仓后续重新开启时，引擎会对已关闭状态进行快照以保留历史盈亏（参见[持仓快照](#持仓快照)）。

## 订单成交聚合

持仓聚合订单成交以维护准确的市场敞口视图。聚合过程处理交易活动的两侧：

### 买入成交

当 BUY 订单成交时：

- 增加多头 (long) 敞口或减少空头 (short) 敞口。
- 更新开仓交易的平均入场价格。
- 更新平仓交易的平均出场价格。
- 计算已平仓部分的已实现盈亏。

### 卖出成交

当 SELL 订单成交时：

- 增加空头敞口或减少多头敞口。
- 更新开仓交易的平均入场价格。
- 更新平仓交易的平均出场价格。
- 计算已平仓部分的已实现盈亏。

### 净持仓计算

持仓维护一个 `signed_qty` 字段表示净敞口：

- 正值表示多头持仓。
- 负值表示空头持仓。
- 零值表示空仓（已关闭）。

```python
# 示例：持仓聚合
# 初始 BUY 100 单位，价格 $50
signed_qty = +100  # 多头持仓

# 后续 SELL 150 单位，价格 $55
signed_qty = -50  # 现在变为空头持仓

# 最终 BUY 50 单位，价格 $52
signed_qty = 0  # 空仓（已关闭）
```

## 持仓调整

持仓调整用于跟踪正常订单成交之外发生的数量或盈亏变化，确保持仓数量准确反映真实的净资产状况。系统会为这些场景生成 `PositionAdjusted` 事件 (event)。

### 基础货币佣金

交易现货货币对（如 BTC/USDT）或外汇现货时，以基础货币支付的佣金会直接影响收到或交付的净数量：

- **开仓成交**：佣金从交易数量中扣除。买入 1.0 BTC 且佣金为 -0.001 BTC 时，净多头持仓为 0.999 BTC。
- **平仓成交**：佣金应用于 `signed_qty`，因为它影响实际库存。卖出 0.999 BTC 的多头持仓且佣金为 -0.000999 BTC 时，你将持有 0.000999 BTC 的空头持仓，而非空仓，因为你实际交出了 0.999999 BTC。
- **翻转**：佣金影响翻转两侧的最终持仓规模。

:::note
基础货币佣金仅适用于现货货币对和外汇现货金融工具，其中佣金币种与 `instrument.base_currency` 一致。对于其他金融工具，佣金单独跟踪，不影响持仓数量。
:::

### 资金费率支付

资金调整用于跟踪永续合约的定期支付，不影响持仓数量。这些调整以 `quantity_change = None` 记录，可能包含盈亏影响。

### 调整跟踪

所有调整都保存在持仓事件历史中：

- `position.adjustments` 返回所有 `PositionAdjusted` 事件的列表。
- 每个调整包含类型（`COMMISSION` 或 `FUNDING`）、数量变化和时间戳。
- 当持仓关闭并重新开启时，调整历史会被清除。当事件被清除时，与已移除成交相关的佣金调整会被重新生成，而非佣金调整（如资金费率）会被保留。

## OMS 类型与持仓管理

NautilusTrader 支持两种主要的 OMS 类型，它们从根本上影响持仓的跟踪和管理方式。还有一个 `OmsType.UNSPECIFIED` 选项，默认使用组件的上下文。详细信息请参阅[执行指南](execution.md#订单管理系统-order-management-system-oms)。

### `NETTING`

在净额模式下，某一金融工具的所有成交聚合到单个持仓中：

- 每个金融工具 ID 一个持仓。
- 所有成交贡献于同一个持仓。
- 随着净数量变化，持仓在多头和空头之间翻转。
- 历史快照保留已关闭的持仓状态。

:::note NETTING 模式下的持仓 ID 分配规则

在净额 OMS 中，持仓 ID 由**首次建仓成交**所属订单的 `client_order_id` 衍生生成：

- **首次建仓**：当某金融工具的第一笔成交到达时，系统创建持仓并分配持仓 ID（`ExecutionEngine` 内部基于首笔订单 ID 生成）。
- **后续成交**：同一金融工具的后续成交聚合到已有持仓，持仓 ID 不变。
- **持仓关闭后重新开仓**：旧持仓被快照，新的首笔成交会触发新持仓创建，并分配基于新订单 ID 的持仓 ID。

实践建议：不要在策略中硬编码或缓存持仓 ID——使用 `self.cache.positions(instrument_id=instrument_id)` 或 `self.cache.position_id(instrument_id=instrument_id)` 动态获取当前净额持仓的 ID。
:::

### `HEDGING`

在对冲模式下，同一金融工具可以存在多个持仓：

- 可同时持有多个多头和空头持仓。
- 每个持仓有唯一的持仓 ID。
- 持仓独立跟踪。
- 不会自动跨持仓净额。
- 已关闭的持仓保留在缓存历史中但不会重新开启；新的成交会创建新的持仓。

:::warning
使用对冲模式时，请注意保证金要求的增加，因为每个持仓独立消耗保证金。某些交易场所 (venue) 可能不支持真正的对冲模式，会自动将持仓净额化。
:::

### 策略 OMS 与交易场所 OMS

平台允许为策略和交易场所设置不同的 OMS 配置：

| 策略 OMS    | 交易场所 OMS  | 行为                          |
| --------- | --------- | --------------------------- |
| `NETTING` | `NETTING` | 策略和交易场所层面均为每个金融工具单一持仓。      |
| `HEDGING` | `HEDGING` | 两个层面均支持多持仓。                 |
| `NETTING` | `HEDGING` | 交易场所跟踪多持仓，Nautilus 维护单一持仓。  |
| `HEDGING` | `NETTING` | 交易场所跟踪单一持仓，Nautilus 维护虚拟持仓。 |

:::tip
对于大多数交易场景，保持策略和交易场所 OMS 类型一致可简化持仓管理。覆盖配置主要适用于自营交易台或与遗留系统对接的场景。参见[实盘指南](live.md)了解特定交易场所的 OMS 配置。
:::

## 持仓快照

持仓快照是净额 OMS 配置中的重要功能，用于保留已关闭持仓的状态，以实现准确的盈亏跟踪和报告。

### 快照的重要性

在净额系统中，当持仓关闭（变为空仓）后又因新交易重新开启时，持仓对象会被重置以跟踪新的敞口。如果没有快照，前一个持仓周期的历史已实现盈亏将会丢失。

### 工作原理

当净额持仓关闭后又收到同一金融工具的新成交时，执行引擎会在重置持仓之前对已关闭状态进行快照，保留以下信息：

- 最终数量和价格。
- 已实现盈亏。
- 所有成交事件。
- 佣金总计。

该快照按持仓 ID 索引存储在缓存中。然后持仓为新周期重置，而先前的快照仍然可访问。投资组合跨所有快照聚合盈亏以获得准确的总计。

:::note
此历史快照机制不同于可选的持仓状态快照（`snapshot_positions`），后者定期记录开仓持仓状态用于遥测。参见[实盘指南](live.md)了解 `snapshot_positions` 和 `snapshot_positions_interval_secs` 设置。
:::

### 示例场景

```python
# 净额 OMS 示例
# 周期 1：开多头持仓
BUY 100 units at $50   # 持仓开启
SELL 100 units at $55  # 持仓关闭，盈亏 = $500
# 快照保留 $500 已实现盈亏

# 周期 2：开空头持仓
SELL 50 units at $54   # 持仓重新开启（空头）
BUY 50 units at $52    # 持仓关闭，盈亏 = $100
# 快照保留 $100 已实现盈亏

# 总已实现盈亏 = $500 + $100 = $600（来自快照）
```

没有快照机制，只有最近一个周期的盈亏可用，导致报告和分析不准确。

## 盈亏计算

NautilusTrader 提供全面的盈亏计算，考虑了金融工具规格和市场惯例。

### 已实现盈亏

在持仓部分或全部平仓时计算：

```python
# 标准金融工具
realized_pnl = (exit_price - entry_price) * closed_quantity * multiplier

# 反向合约（方向相关）
# 多头: realized_pnl = closed_quantity * multiplier * (1/entry_price - 1/exit_price)
# 空头: realized_pnl = closed_quantity * multiplier * (1/exit_price - 1/entry_price)
```

引擎根据持仓方向自动应用正确的公式。

:::note 什么是反向合约？
**反向合约**（inverse contract）是加密货币衍生品市场中的常见合约类型（如 BitMEX XBTUSD），其特点是以**基础货币**（如 BTC）而非报价货币（如 USD）进行结算。

因为结算货币是基础货币，盈亏需要通过价格的倒数（`1/price`）来换算，导致公式与标准合约不同。这也带来了**非线性特性**——以做多为例，价格下跌时亏损的 BTC 数量会比同等幅度价格上涨时盈利的 BTC 数量更大，因为价格越低，同样的 USD 波动换算成 BTC 的金额越大。

**示例（反向 BTC/USD，面值 100 USD）：**

- 做多 $50,000 → $60,000：PnL = 100 × (1/50000 - 1/60000) = **+0.000333 BTC**
- 做多 $50,000 → $40,000：PnL = 100 × (1/50000 - 1/40000) = **-0.000500 BTC**（亏损更大）
:::

### 未实现盈亏

使用当前市场价格为未平仓持仓计算。`price` 参数接受任何参考价格（买价、卖价、中间价、最新价或标记价）：

```python
position.unrealized_pnl(last_price)  # 使用最新成交价
position.unrealized_pnl(bid_price)  # 多头持仓的保守估计
position.unrealized_pnl(ask_price)  # 空头持仓的保守估计
```

对于空仓持仓，无论提供什么价格，都返回 `Money(0, settlement_currency)`。

### 总盈亏

合并已实现和未实现部分：

```python
total_pnl = position.total_pnl(current_price)
# 返回 realized_pnl + unrealized_pnl
```

### 币种考量

- 盈亏以金融工具的结算货币计算。
- 对于外汇，通常是报价货币。
- 对于反向合约，盈亏可能以基础货币计算。
- 投资组合按金融工具以结算货币聚合已实现盈亏。
- 多币种总计需要在 `Position` 类外部进行转换。

## 佣金与费用

持仓跟踪所有交易成本：

- 佣金按币种累计。
- 每笔成交的佣金加入累计总额。
- 支持多种佣金币种。
- 已实现盈亏仅在佣金以结算货币计价时包含佣金。
- 其他币种的佣金单独跟踪，可能需要转换。

```python
commissions = position.commissions()
# 返回 list[Money]，包含按币种聚合的佣金总计

notional = position.notional_value(current_price)
# 返回以报价货币（标准）或基础货币（反向）计价的 Money
```

**限制：**

- 如果反向金融工具未设置 `base_currency`，将会触发 panic。
- 不处理 quanto 合约（返回报价货币而非结算货币）。
- 对于 quanto 金融工具，请使用 `instrument.calculate_notional_value()` 代替。

:::note 什么是 Quanto 合约？
**Quanto 合约**（quantity-adjusted contract）是一种跨币种结算的衍生品合约：标的以 A 货币计价，但盈亏以 B 货币按**固定汇率**结算，从而消除汇率风险。

| 类型         | 标的计价 | 结算货币 | 汇率风险        | 典型例子             |
| ---------- | ---- | ---- | ----------- | ---------------- |
| 线性（标准）     | USD  | USD  | 无           | Binance BTCUSDT  |
| 反向         | USD  | BTC  | 有（非线性 PnL）  | BitMEX XBTUSD    |
| **Quanto** | USD  | BTC  | **无**（固定汇率） | BitMEX 早期 ETHUSD |

**示例（BitMEX ETHUSD quanto 永续，固定乘数 0.000001 BTC/USD）：** 做多 10,000 张，ETH 从 $2,000 涨到 $2,100 → PnL = (2100 - 2000) × 10000 × 0.000001 = **1.0 BTC**，无论 BTC/USD 汇率如何变化。

Quanto 的结算货币（如 BTC）既不是报价货币（USD）也不是基础货币（ETH），而是第三种货币。`Position` 类只处理线性和反向两种情况，无法自动识别这个固定换算关系，因此需要使用 `instrument.calculate_notional_value()` 代替。
:::

## 持仓属性与状态

### 标识符

- `id`：唯一持仓标识符。
- `instrument_id`：交易的金融工具。
- `account_id`：持仓所在的账户。
- `trader_id`：持仓所有者的交易者。
- `strategy_id`：管理该持仓的策略。
- `opening_order_id`：开仓的客户端订单 ID。
- `closing_order_id`：平仓的客户端订单 ID。

### 持仓状态

- `side`：当前持仓方向（`LONG`、`SHORT` 或 `FLAT`）。
- `entry`：当前持仓的入场方向（多头为 `Buy`，空头为 `Sell`）。持仓翻转时更新。
- `quantity`：当前持仓绝对规模。
- `signed_qty`：带符号的持仓规模（多头为正，空头为负）。
- `peak_qty`：持仓生命周期中达到的最大数量。
- `is_open`：持仓是否当前处于开仓状态。
- `is_closed`：持仓是否已关闭（空仓）。
- `is_long`：持仓方向是否为多头。
- `is_short`：持仓方向是否为空头。

### 定价与估值

- `avg_px_open`：平均入场价格。
- `avg_px_close`：平仓时的平均出场价格。
- `realized_pnl`：已实现盈亏。
- `realized_return`：已实现收益率，以小数表示（如 0.05 表示 5%）。
- `quote_currency`：金融工具的报价货币。
- `base_currency`：基础货币（如适用）。
- `settlement_currency`：盈亏结算货币。

### 金融工具规格

- `multiplier`：合约乘数。
- `price_precision`：价格的小数精度。
- `size_precision`：数量的小数精度。
- `is_inverse`：是否为反向金融工具。

### 时间戳

- `ts_init`：持仓初始化时间。
- `ts_opened`：持仓开仓时间。
- `ts_last`：最后更新时间戳。
- `ts_closed`：持仓平仓时间。
- `duration_ns`：从开仓到平仓的持续时间（纳秒）。

### 关联数据

- `symbol`：金融工具的交易代码。
- `venue`：交易场所。
- `client_order_ids`：与持仓关联的所有客户端订单 ID。
- `venue_order_ids`：与持仓关联的所有交易场所订单 ID。
- `trade_ids`：来自交易场所的所有交易/成交 ID。
- `events`：应用于持仓的所有订单成交事件。
- `event_count`：已应用的成交事件总数。
- `last_event`：最近的成交事件。
- `last_trade_id`：最近的交易 ID。

:::info
有关完整的类型信息和详细的属性文档，请参阅 Position [API 参考](../../docs/api_reference/model/position.md)。
:::

## 事件与跟踪

持仓维护完整的事件历史：

- 所有订单成交事件按时间顺序存储。
- 跟踪关联的客户端订单 ID。
- 保留来自交易场所的交易 ID。
- 事件计数表示已应用的成交总数。

这些历史数据支持：

- 详细的持仓分析。
- 交易对账。
- 绩效归因。
- 审计追踪。

:::tip
使用 `position.events` 访问完整的成交历史以进行对账。
`position.trade_ids` 属性有助于与经纪商对账单进行匹配。
参见[执行指南](execution.md)了解对账最佳实践。
:::

## 数值精度

持仓计算使用 64 位浮点数（`f64`）进行盈亏和平均价格计算。虽然定点类型（`Price`、`Quantity`、`Money`）在配置的小数位数上保持精确精度，但内部计算会转换为 `f64` 以获得性能和溢出安全性。

### 设计原理

平台对持仓计算使用 `f64` 以平衡性能和精度：

- 浮点运算比任意精度运算快得多。
- 原始整数乘法即使使用 128 位整数也可能溢出。
- 每次计算都从精确的定点值开始，避免累积误差。
- IEEE-754 双精度提供约 15 位十进制精度。

### 经验证的精度特性

测试确认 `f64` 运算在典型交易场景中保持精度：

- 标准金额：标准货币中 >= 0.01 的金额无精度损失。
- 高精度金融工具：9 位小数的加密货币价格在 1e-6 容差内保持精度。
- 连续成交：100 笔成交无漂移（佣金精度达 1e-10）。
- 极端价格：处理从 0.00001 到 99,999.99999 的范围无溢出。
- 往返交易：以相同价格开仓和平仓产生精确的盈亏（仅含佣金）。

实现细节请参阅 `crates/model/src/position.rs` 中的 `test_position_pnl_precision_*` 测试。

:::note
对于需要精确十进制运算的监管合规或审计追踪，请考虑使用外部库的 `Decimal` 类型。低于 `f64` 最小精度（约 1e-15）的极小金额可能会被舍入为零。这不影响使用标准货币精度（通常 2-9 位小数）的实际交易场景。
:::

## 与其他组件的集成

持仓与几个关键组件交互：

- **Portfolio**：跨金融工具和策略聚合持仓。
- **ExecutionEngine**：从成交创建和更新持仓。
- **Cache**：存储持仓状态和快照。
- **RiskEngine**：监控持仓限制和敞口。

:::note
不会为价差金融工具创建持仓。虽然条件订单仍可为价差触发，但它们在没有持仓关联的情况下运行。引擎将价差金融工具与常规持仓分开处理。
:::

## 总结

持仓是 NautilusTrader 中跟踪交易活动和绩效的核心。理解持仓如何聚合成交、计算盈亏以及处理不同的 OMS 配置，对于构建稳健的交易策略至关重要。持仓快照机制确保了净额模式下准确的历史跟踪，而全面的事件历史则支持详细的分析和对账。
